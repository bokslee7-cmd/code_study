## 작업 요약
로그인한 사용자에게 "출입증"을 만들어 주고, 그 출입증이 진짜인지 확인하고, 오래된 출입증을 새것으로 바꿔 주는 `TokenService`를 만들었다. 출입증은 두 장이다. 하나는 하루 종일 쓰는 게 아니라 15분짜리 **일회용 방문증(액세스 토큰)**이고, 다른 하나는 7일 동안 방문증을 다시 받을 수 있게 해 주는 **재발급 증서(리프레시 토큰)**다. 방문증은 경비실(서버)이 장부를 보지 않고 도장만 보고 통과시키지만, 재발급 증서는 경비실 장부(DB)에 "몇 번 증서가 발급됐다"고 적어 두고 쓸 때마다 대조한다.

| 기능 | 하는 일 | 실패 시 |
|------|---------|---------|
| `create_tokens(user_id)` | 두 토큰을 만들고, 재발급 증서의 지문(SHA-256)과 만료 시각을 DB에 저장 | - |
| `verify_access_token(token)` | 도장(서명)·유효기간·종류를 확인하고 사용자 ID를 돌려줌 | 401 |
| `verify_refresh_token(token)` | 위 확인 + 장부에 있는지, 폐기·만료되지 않았는지 확인 | 401 |
| `rotate(token)` | 증서를 검증한 뒤 폐기하고, 같은 사용자의 새 두 토큰을 발급 | 401 |

화면이나 HTTP는 모르고 세션만 받아 일한다(헌법 III). 이 서비스를 `/auth/login`(T029), `/auth/refresh`(T031), 인증 의존성(T027)이 가져다 쓴다.

## 기술 결정
- **토큰 생성·해독은 `utils/jwt.py`를 그대로 사용**: 만료 시간(15분/7일)과 비밀키 읽기는 이미 T012에서 만들어 두었다. 서비스는 "언제 무엇을 DB에 적는가"만 책임진다.
- **DB 만료 시각을 토큰 안의 `exp`에서 가져옴**: 따로 7일을 계산하면 환경변수(`JWT_REFRESH_TOKEN_DAYS`)를 바꿨을 때 토큰과 장부의 시각이 어긋난다. 토큰을 만든 뒤 그 값을 읽어 같은 시각을 적었다(테스트로 확인).
- **교체할 때 장부 행을 잠금(`FOR UPDATE`)**: 같은 재발급 증서로 요청 두 개가 동시에 들어오면 둘 다 "아직 유효"로 보고 새 토큰을 받아 갈 수 있다. 행을 잠가 한 요청이 끝난 뒤에야 다른 요청이 확인하게 했다. 늦게 온 요청은 폐기된 증서를 보고 401을 받는다.
- **실패 메시지는 둘로만 나눔**: "만료됨"과 "올바르지 않음". 폐기됨·장부에 없음·종류 틀림·서명 위조·형식 오류는 모두 같은 "올바르지 않음"이다. 어떤 이유로 거절됐는지 알려 주면 공격자에게 힌트가 된다. 만료만 따로 둔 것은 프런트엔드가 "다시 로그인" 안내를 보여 주기 위해서다. 라이브러리의 영어 오류 문구도 노출하지 않는다.
- **`sub`가 UUID가 아니면 거절**: 서명이 맞아도 사용자 ID 형식이 아니면 뒤 단계에서 오류가 나기 전에 401로 막는다.
- **서비스는 `flush`만, `commit`은 하지 않음**: UserService와 같은 이유다. 한 요청 안에서 "구 토큰 폐기 + 새 토큰 저장"이 함께 성공하거나 함께 취소된다.

## 비고
- **DB 연동 검증은 하지 못했다.** Docker/PostgreSQL이 꺼져 있어(T023~T025와 같음) 테스트는 세션을 대역(mock)으로 바꿨다. 실제 DB가 있어야 확인되는 항목은 다음과 같다. Docker를 켠 뒤 통합 테스트로 추가하길 권한다.
  - `FOR UPDATE`가 실제로 동시 요청을 줄 세우는지 (테스트는 SQL에 문구가 들어갔는지만 본다)
  - 저장 후 `token_hash` 유일성 제약과 `expires_at` 시간대 처리
- **재사용 감지는 하지 않았다.** 이미 폐기된 증서가 다시 오면 그 요청만 401로 거절하고, 해당 사용자의 다른 증서까지 모두 폐기하지는 않는다. 사용자가 탭 두 개로 동시에 갱신하면 정상 사용자가 로그아웃될 수 있어서다. 요구사항 보충(FR-110)의 "토큰 재사용 시도 로그"와 함께 필요하면 별도 태스크로 다루면 된다.
- **비밀번호 변경 시 전체 폐기(요구사항 보충)는 이 태스크 범위가 아니다.** 비밀번호 변경 기능이 생길 때 만든다.
- **`device_info`는 다루지 않는다.** 현재 `refresh_tokens` 테이블에 그 칸이 없고(T009 마이그레이션), 세션 목록 화면은 Phase 2다.
