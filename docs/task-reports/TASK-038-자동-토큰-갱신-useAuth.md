# TASK-038. 자동 토큰 갱신 (useAuth)

## 상태
완료

## 날짜

## 작업 요약
출입증(액세스 토큰)은 15분짜리 일회권이라 쓰는 도중에 만료되기 쉽다. 이번 작업은 도서관 안내 데스크에 "만료 1분 전에 새 출입증으로 슬쩍 바꿔 주는 직원"과 "다시 방문한 사람의 얼굴(쿠키)로 출입증을 재발급해 주는 직원"을 둔 것이다. 둘 다 `frontend/src/hooks/useAuth.ts`에 있다.

**`useAuthSession()`** - 앱 최상단(`App`)에서 한 번만 호출한다.
1. **세션 복구**: 앱이 시작되면 `refresh()`(쿠키) -> `fetchMe(새 토큰)` 순서로 호출해 사용자와 토큰을 한 번에 저장한다. 실패하면 비로그인으로 확정한다. 어느 쪽이든 끝나면 `isRestoring`을 `false`로 내린다. 이 값이 `true`인 동안 `ProtectedRoute`는 로딩 문구를 보여 준다.
2. **자동 갱신**: 스토어의 `tokenExpiresAt`를 보고, 만료 60초 전에 `refresh()`를 호출해 토큰을 교체한다. 교체하면 새 만료 시각이 저장되므로 다음 갱신이 자동으로 이어서 예약된다. 로그아웃(`clearSession`)하거나 컴포넌트가 사라지면 예약이 취소된다.
3. **갱신 실패**(401 등): `clearSession()`으로 로그아웃 상태가 된다.

**`useAuth()`** - `{ user, isAuthenticated, logout }`. `logout`은 서버에 요청을 보내고, 성공/실패와 무관하게 로컬 세션을 반드시 지운 뒤 `/login`으로 이동한다.

## 기술 결정
- **스토어에 `tokenExpiresAt`/`isRestoring` 추가**: 훅끼리 상태를 나누려면 스토어가 가장 가볍다. 추가 필드와 선택 인자만 넣어서 기존 `auth-store.test.ts` 8개는 수정 없이 통과한다. 로그인(T036)과 갱신이 같은 경로로 타이머를 움직이게 하려고 만료 "시각"을 스토어에 둔다.
- **StrictMode 이중 실행 대응**: 개발 모드에서는 effect가 두 번 돈다. 리프레시 토큰은 한 번 쓰면 교체(회전)될 수 있어서, 두 번째 호출이 401을 받아 멀쩡한 사용자를 로그아웃시킬 위험이 있다. `useRef`로 복구가 이미 시작됐는지 기록해 한 번만 실행한다(테스트로 고정).
- **갱신 응답을 기다리는 중 로그아웃되면 토큰을 되살리지 않음**: 이 경우 새 토큰만 있고 사용자는 없는 반쪽 세션이 생긴다. 응답 도착 시점에 스토어 토큰이 `null`이면 버린다(테스트로 고정).
- **갱신 실패는 종류와 상관없이 로그아웃 처리**: 지침의 최소 요구는 401이지만, 네트워크 오류로 갱신에 실패해도 현재 토큰은 곧 만료되고 다시 시도할 예약도 남지 않는다. 반쪽 상태로 두기보다 깔끔히 로그아웃하는 편이 사용자에게 예측 가능하다. 재시도/백오프는 요구되지 않아 만들지 않았다(YAGNI).
- **401 응답 시 refresh 1회 후 재시도(인터셉터 방식)는 생략**: 지침이 "과하면 생략 가능"이라 했다. 만료 60초 전 선제 갱신과 시작 시 복구만으로 정상 흐름이 모두 덮인다. 인터셉터 방식은 동시에 여러 요청이 401을 받을 때 갱신을 한 번으로 합치는 대기열, 무한 재시도 방지, 순환 의존 회피(api-client가 스토어/서비스를 가리키지 않기 위한 주입 구조)가 함께 필요해 복잡도가 크게 늘어난다. 지금은 보호된 데이터 API가 하나도 없어 실제 이득도 없다. 실제 API를 붙이는 단계에서 필요하면 별도 태스크로 도입한다.
- **갱신 여유 시간 60초 고정**: 서버 만료 15분 기준으로 충분하다. 만료까지 60초 이하로 남은 상태라면 지연 0으로 즉시 갱신한다.
- **`useAuth().logout`만 제공하고 버튼은 만들지 않음**: 대시보드가 placeholder라서 붙일 화면이 없다. T042(수동 테스트)가 시작되기 전에 대시보드나 헤더에서 이 함수를 쓰면 된다.
