## 작업 요약
`backend/src/tasks/celery_app.py`에 백그라운드 작업을 보내고 받을 Celery 앱을 구성했다. 앱은 `REDIS_URL` 환경 변수에서 연결 주소를 읽어 Redis를 작업 전달소와 결과 보관소 양쪽에 사용한다. 환경 변수가 없거나 공백뿐이면 앱이 잘못된 주소로 조용히 동작하지 않도록, 무엇이 필요한지 알려 주는 오류를 낸다.

작업은 네 개의 대기 줄(`default`, `document_generation`, `practice_generation`, `cleanup`) 중 알맞은 곳으로 보낼 수 있게 준비했다. 기본 줄은 `default`이며, 별도로 제출된 작업은 최대 300초 안에 끝나도록 제한한다. 작업 내용과 결과는 JSON 형식만 받도록 정해 불필요한 직렬화 형식은 허용하지 않는다. 모든 시간 기준은 UTC로 맞췄다. Celery 앱의 기본 이름은 `code_learning`이며, 안내 문서의 `celery -A src.tasks.celery_app worker` 방식으로 찾을 수 있다.

비유하면 Redis는 작업 요청을 접수하고 완료 결과를 보관하는 우편함이고, Celery는 그 우편함을 확인해 일을 처리하는 직원이다. 대기 줄은 업무별 접수 창구와 같다. 이번 작업은 창구와 전달 경로만 준비했으며, 실제 문서 생성이나 연습 문제 생성 함수는 후속 기능에서 해당 줄을 사용하게 된다.

## 기술 결정
- 저장소의 기존 설정 방식과 맞춰 `.env` 파일을 암묵적으로 읽지 않고 `REDIS_URL`을 직접 사용한다. 설정이 빠진 경우 시작 시 명시적으로 실패시켜, 잘못된 주소로 작업을 보내는 상황을 방지한다.
- 연결 주소 하나를 브로커와 결과 저장소에 공용으로 사용한다. 기존 `.env.example`과 빠른 시작 안내에 이미 같은 Redis 주소가 정의되어 있어 추가 의존성이나 환경 키가 필요하지 않다.
- 기본 큐와 세 기능별 큐를 미리 선언하되, 아직 존재하지 않는 작업 함수의 라우팅 규칙까지 만들지는 않았다. 각 작업이 추가될 때 해당 큐를 지정할 수 있도록 현재 범위를 기반 설정에 한정했다.
- Celery와 Kombu 패키지가 정적 타입 표시를 제공하지 않아 import 두 곳에만 타입 검사 예외를 지정했다. 애플리케이션 설정 자체의 타입 검사는 통과했다.

## 비고
검증은 Redis 서버에 실제로 작업을 보내지 않고 설정 및 Celery CLI 앱 탐색을 확인하는 방식으로 진행했다. 따라서 실행 환경에서 워커를 사용하려면 Redis가 실행 중이고 `REDIS_URL`이 해당 서버를 가리켜야 한다. 다음에는 문서 생성·연습 문제·정리 작업에서 큐를 지정하는 태스크를 추가하면 된다.
